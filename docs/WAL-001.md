# WAL-001 — Crear mi billetera

Implemento el contrato de creación explícita de billetera del Incremento 2. Uso ARS como moneda acordada y saldo decimal(18,2). Parto de develop después de integrar TEST-001; no modifico el registro para crear billeteras automáticamente.

## Contrato

- **Operación:** crearBilletera().
- **Referencia:** historia WAL-001; caso de uso Crear Billetera.
- **Actor:** usuario autenticado con rol Client.
- **Precondiciones:** cuenta existente y activa, token y versión de sesión válidos, permiso Client; esquema SQL migrado para completar la operación.
- **Postcondiciones de creación:** creo una instancia Wallet persistida, la asocio exclusivamente al usuario autenticado y asigno Id, saldo cero, ARS y fecha UTC. No creo movimientos.
- **Postcondiciones de repetición:** recupero la billetera existente sin modificar su Id, saldo, moneda, fecha o titular.
- **Cardinalidad:** un usuario tiene cero o una billetera; cada billetera tiene exactamente un usuario. Impido duplicados mediante índice SQL único, también ante concurrencia.

## HTTP

Envío una solicitud sin cuerpo:

```http
POST /api/wallets
Authorization: Bearer <accessToken>
Accept: application/json
```

Recibo 201 al crear o 200 cuando ya existe, con el mismo esquema JSON:

```json
{
  "id": "a5d3096e-8d5e-4e42-b7a7-e1c2d5c67908",
  "balance": 0.00,
  "currency": "ARS",
  "createdAt": "2026-10-25T18:00:00Z"
}
```

El saldo de una billetera existente puede ser distinto de cero; no lo reinicio. No recibo UserId, saldo ni moneda desde el cliente y no devuelvo datos internos. No incluyo Location hacia un endpoint de consulta aún no implementado.

| HTTP | Código | Comportamiento |
|---|---|---|
| 400 | INVALID_INPUT | Rechazo cualquier cuerpo no vacío, incluido {}, espacios y cuerpo chunked. |
| 401 | HTTP_401 | Rechazo token ausente, inválido, expirado o sesión revocada/inactiva. |
| 403 | HTTP_403 | Rechazo una sesión válida sin permiso Client. |
| 503 | IDENTITY_NOT_CONFIGURED | Mantengo el comportamiento base cuando identidad está deshabilitada. |
| 503 | STORAGE_UNAVAILABLE | Informo indisponibilidad SQL sin detalles internos. |
| 500 | REQUEST_FAILED | Informo falla inesperada sin revelar información sensible. |

Uso ProblemDetails para errores y no-store en respuestas. Si se pierde la respuesta después de guardar, puedo repetir la creación: obtengo el recurso existente. No necesito una clave de idempotencia adicional para esta operación porque el usuario sólo puede tener una billetera.

## Implementación

- En Domain defino Wallet con creación controlada y sin métodos para cargar o transferir saldo.
- En Application coordino el usuario actual, el reloj, el repositorio y el DTO público.
- En Infrastructure consulto la billetera y guardo sólo si falta. Si otra solicitud gana la carrera de creación, descarto el candidato fallido y leo la billetera persistida.
- En API exijo Client y rechazo el cuerpo antes de ejecutar el caso de uso.
- En SQL impongo FK a Users, UserId único, saldo no negativo, ARS con comparación sensible a mayúsculas y borrado restringido del titular. Conservo RowVersion para concurrencia futura.

## Preparación de la base

Configuro identidad, conexión y clave JWT de forma externa, como describo en el README. Desde la raíz del repositorio ejecuto:

```sh
dotnet tool restore
dotnet ef migrations has-pending-model-changes --project Wallet.Infrastructure --startup-project Wallet.Api
dotnet ef migrations script InitialIdentity CreateWallets --project Wallet.Infrastructure --startup-project Wallet.Api --output migration.sql
```

Reviso el script y confirmo la base autorizada antes de aplicarlo:

```sh
dotnet ef database update --project Wallet.Infrastructure --startup-project Wallet.Api
```

Conservo InitialIdentity y agrego CreateWallets. Los usuarios anteriores permanecen sin billetera hasta solicitarla. El script InitialIdentity.sql histórico no incluye esta tabla; para el esquema actual uso las migraciones.

Para planificar una vuelta atrás genero el script sin ejecutarlo:

```sh
dotnet ef migrations script CreateWallets InitialIdentity --project Wallet.Infrastructure --startup-project Wallet.Api --output rollback-wallets.sql
```

Ese rollback elimina Wallets y sus datos; no lo ejecuto sobre una base con fondos o información que deba conservar sin un plan de recuperación. En esta tarea sólo generé y revisé los scripts: no apliqué ni revertí una base real.
