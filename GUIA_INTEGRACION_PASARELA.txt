================================================================================
GUIA DE INTEGRACION Y FLUJO EXTREMO A EXTREMO (END-TO-END)
PASARELA DE PAGO B2B - WALLET AS A SERVICE
================================================================================

1. INTRODUCCION: COMO FUNCIONA NUESTRA PASARELA PARA COMERCIOS
--------------------------------------------------------------------------------
Nuestra pasarela opera bajo el modelo B2B (Wallet as a Service). En lugar de
depender de un intermediario rigido de usuario final, nuestra API provee
infraestructura financiera a comercios y aplicaciones externas para que
puedan cobrar, transferir fondos y consultar su libro contable en tiempo real.

Cada comercio o aplicacion externa es una entidad de tipo "ExternalClient",
la cual hereda de la jerarquia polimorfica "WalletOwner" y tiene asociada:
- Una clave secreta de acceso: "ApiKey" (autenticacion por cabecera X-Api-Key).
- Una billetera financiera unica: "WalletId" (con saldo en ARS).
- Un libro mayor inmutable: "Movements" (auditoria contable con doble partida).

--------------------------------------------------------------------------------
2. ARQUITECTURA DEL FLUJO DE PAGO
--------------------------------------------------------------------------------
1. Alta del Comercio:
   El comercio se registra una sola vez en la pasarela y obtiene su ApiKey
   y su WalletId.

2. Acreditacion Inicial / Cobro de Fondos:
   El comercio puede recibir pagos de clientes o recargar fondos en su billetera
   (en ambiente de desarrollo usando la herramienta de funding).

3. Registro de Pagos / Transferencias:
   Cuando se concreta una transaccion en la aplicacion externa, esta envia
   un request a la pasarela con su ApiKey y un UUID unico de Idempotencia.
   La pasarela debita el origen, acredita el destino y genera los movimientos
   contables en una transaccion atomica SQL.

4. Idempotencia y Reintentos Seguros:
   Si la conexion se interrumpe y la aplicacion del comercio reintenta con la
   misma Idempotency-Key, la pasarela responde con el resultado original y la
   cabecera "Idempotency-Replayed: true" sin debitar dos veces el dinero.

5. Conciliacion Contable:
   El comercio puede consultar su saldo actualizado y su historial de movimientos
   en cualquier momento.


================================================================================
3. PASO A PASO: GUIA DE EJECUCION DE EXTREMO A EXTREMO
================================================================================
Requisitos previos:
- Servidor ejecutandose en:
  HTTP:  http://localhost:5081
  HTTPS: https://localhost:7081
(Podes usar curl en Windows/Linux o Invoke-RestMethod en PowerShell).


--------------------------------------------------------------------------------
PASO 1: REGISTRAR AL COMERCIO (ONBOARDING B2B)
--------------------------------------------------------------------------------
La aplicacion externa se da de alta en la pasarela.

Comando (PowerShell):
$body = @{
    companyName = "Mi Tienda Online S.A."
    contactEmail = "pagos@mitienda.com"
    description = "Pasarela de cobro para compras web"
} | ConvertTo-Json

$comercio = Invoke-RestMethod -Uri "http://localhost:5081/api/v1/gateway/clients" `
    -Method Post -ContentType "application/json" -Body $body

$comercio | ConvertTo-Json

Comando alternativo (cURL):
curl -X POST http://localhost:5081/api/v1/gateway/clients \
  -H "Content-Type: application/json" \
  -d '{"companyName":"Mi Tienda Online S.A.","contactEmail":"pagos@mitienda.com","description":"Pasarela de cobro para compras web"}'

Respuesta esperada (HTTP 201 Created):
{
  "id": "6b234a54-48c3-444f-9b32-4ea9934e45f3",
  "companyName": "Mi Tienda Online S.A.",
  "contactEmail": "pagos@mitienda.com",
  "description": "Pasarela de cobro para compras web",
  "apiKey": "7e0e1b08c75907c5c7996353ee699a928bcd1ec78c14778535c25381fb9b3d9b",
  "walletId": "61c28438-6930-41df-9e3b-ccf70d3680a9",
  "createdAt": "2026-10-31T03:20:04Z"
}

* NOTA IMPORTANTE: Guarda la "apiKey" y el "walletId", ya que se usaran en los siguientes pasos.


--------------------------------------------------------------------------------
PASO 2: CONSULTAR SALDO DE LA BILLETERA DEL COMERCIO
--------------------------------------------------------------------------------
Para consultar el saldo disponible, el comercio envia su ApiKey en la cabecera
"X-Api-Key".

Comando (PowerShell):
$headers = @{ "X-Api-Key" = "7e0e1b08c75907c5c7996353ee699a928bcd1ec78c14778535c25381fb9b3d9b" }
$billetera = Invoke-RestMethod -Uri "http://localhost:5081/api/v1/gateway/wallet" `
    -Method Get -Headers $headers
$billetera | ConvertTo-Json

Comando alternativo (cURL):
curl -X GET http://localhost:5081/api/v1/gateway/wallet \
  -H "X-Api-Key: 7e0e1b08c75907c5c7996353ee699a928bcd1ec78c14778535c25381fb9b3d9b"

Respuesta esperada (HTTP 200 OK):
{
  "id": "61c28438-6930-41df-9e3b-ccf70d3680a9",
  "balance": 0.00,
  "currency": "ARS",
  "createdAt": "2026-10-31T03:20:04Z"
}


--------------------------------------------------------------------------------
PASO 3: RECARGA DE SALDO PARA PRUEBAS (DEVELOPMENT FUNDING)
--------------------------------------------------------------------------------
En ambiente de desarrollo, inyectamos fondos ficticios auditados a la billetera
del comercio mediante la herramienta oficial CLI:

Comando (PowerShell):
$env:DOTNET_ENVIRONMENT = "Development"
dotnet run --project Wallet.DevelopmentTools -- fund-wallet `
  --wallet-id 61c28438-6930-41df-9e3b-ccf70d3680a9 `
  --amount 10000.00 `
  --idempotency-key 11111111-1111-1111-1111-111111111111 `
  --server "(localdb)\MSSQLLocalDB" `
  --database "WalletDb" `
  --confirm-development-database

Respuesta en consola:
{"id":"...","walletId":"61c28438-...","amount":10000.00,"currency":"ARS","balanceAfter":10000.00,"created":true}

Si vuelves a ejecutar el PASO 2, veras que el saldo se actualizo exactamente a 10000.00 ARS.


--------------------------------------------------------------------------------
PASO 4: DAR DE ALTA UN COMERCIO DESTINO O CUENTA RECEPTORA
--------------------------------------------------------------------------------
Registramos un segundo cliente (por ejemplo, un proveedor o comercio receptor):

Comando (PowerShell):
$bodyDest = @{
    companyName = "Proveedor Mayorista S.R.L."
    contactEmail = "finanzas@mayorista.com"
    description = "Cuenta recaudadora de pagos mayoristas"
} | ConvertTo-Json

$receptor = Invoke-RestMethod -Uri "http://localhost:5081/api/v1/gateway/clients" `
    -Method Post -ContentType "application/json" -Body $bodyDest

$receptor | ConvertTo-Json

Supongamos que el walletId obtenido del receptor es:
"c160301c-9575-4e37-8eed-82cd513f60b6"


--------------------------------------------------------------------------------
PASO 5: PROCESAR UN PAGO / TRANSFERENCIA DESDE LA PASARELA
--------------------------------------------------------------------------------
El comercio emisor transfiere fondos al comercio receptor.
Se requiere obligatoriamente:
- Cabecera "X-Api-Key": la clave secreta del comercio emisor.
- Cabecera "Idempotency-Key": un identificador UUID unico generado por la app.

Comando (PowerShell):
$idempotencyKey = [Guid]::NewGuid().ToString()

$paymentBody = @{
    destinationWalletId = "c160301c-9575-4e37-8eed-82cd513f60b6"
    amount = 2500.50
} | ConvertTo-Json

$headers = @{
    "X-Api-Key" = "7e0e1b08c75907c5c7996353ee699a928bcd1ec78c14778535c25381fb9b3d9b"
    "Idempotency-Key" = $idempotencyKey
}

$pago = Invoke-RestMethod -Uri "http://localhost:5081/api/v1/gateway/payments" `
    -Method Post -ContentType "application/json" -Headers $headers -Body $paymentBody

$pago | ConvertTo-Json

Comando alternativo (cURL):
curl -i -X POST http://localhost:5081/api/v1/gateway/payments \
  -H "Content-Type: application/json" \
  -H "X-Api-Key: 7e0e1b08c75907c5c7996353ee699a928bcd1ec78c14778535c25381fb9b3d9b" \
  -H "Idempotency-Key: aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee" \
  -d '{"destinationWalletId":"c160301c-9575-4e37-8eed-82cd513f60b6","amount":2500.50}'

Respuesta esperada (HTTP 201 Created):
Headers:
  Idempotency-Replayed: false
Body:
{
  "id": "6b7186c2-5e69-4b03-a054-fdb5b03478a6",
  "sourceWalletId": "61c28438-6930-41df-9e3b-ccf70d3680a9",
  "destinationWalletId": "c160301c-9575-4e37-8eed-82cd513f60b6",
  "amount": 2500.50,
  "currency": "ARS",
  "status": "Completed",
  "createdAt": "2026-10-31T03:44:11Z"
}

PASO 6: COMPROBAR LA GARANTIA DE IDEMPOTENCIA
--------------------------------------------------------------------------------
Si la aplicacion del comercio sufre un corte de conexion y reintenta el cobro
enviando EXACTAMENTE la misma Idempotency-Key anterior:

Comando:
(Re-ejecutar el comando del Paso 5 con la misma Idempotency-Key)

Respuesta esperada (HTTP 200 OK):
Headers:
  Idempotency-Replayed: true
Body:
(Mismo JSON que en el paso 5. El saldo NO se desconto por segunda vez).


--------------------------------------------------------------------------------
PASO 7: COMPROBAR RECHAZO POR SALDO INSUFICIENTE
--------------------------------------------------------------------------------
Si el comercio intenta enviar un importe superior a su saldo actual (7499.50 ARS),
por ejemplo 50000.00 ARS:

Comando:
$headers = @{
    "X-Api-Key" = "7e0e1b08c75907c5c7996353ee699a928bcd1ec78c14778535c25381fb9b3d9b"
    "Idempotency-Key" = [Guid]::NewGuid().ToString()
}
$body = @{
    destinationWalletId = "c160301c-9575-4e37-8eed-82cd513f60b6"
    amount = 50000.00
} | ConvertTo-Json

Invoke-RestMethod -Uri "http://localhost:5081/api/v1/gateway/payments" `
    -Method Post -ContentType "application/json" -Headers $headers -Body $body

Respuesta esperada (HTTP 409 Conflict):
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.10",
  "title": "Saldo insuficiente en la billetera del cliente.",
  "status": 409,
  "code": "INSUFFICIENT_FUNDS"
}


--------------------------------------------------------------------------------

Comando (PowerShell):

$movimientos = Invoke-RestMethod -Uri "http://localhost:5081/api/v1/gateway/movements" `

$movimientos.items | ConvertTo-Json
